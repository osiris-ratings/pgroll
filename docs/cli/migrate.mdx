---
title: Migrate
description: Applies all outstanding migrations from a directory to the target database.
---

## Command

Assuming that migrations up to and including migration `40_create_enum_type` from the [example migrations](https://github.com/xataio/pgroll/tree/main/examples) directory have been applied, running:

```
$ pgroll migrate examples/
```

will apply migrations from `41_add_enum_column` onwards to the target database.

If the `--complete` flag is passed to `pgroll migrate` the final migration to be applied will be completed. Otherwise the final migration will be left active (started but not completed).

If any of the migration files are incompatible with your `pgroll` version, the command will report the errors and exit before running any migrations.

## Backfill Configuration

When migrations involve backfilling data (such as adding a `NOT NULL` constraint to an existing column), the backfill process can be controlled using these flags:

- `--backfill-batch-size`: Number of rows backfilled in each batch (default: 1000)
- `--backfill-batch-delay`: Duration of delay between each batch, e.g., "1s", "1000ms" (default: 0s)

```
$ pgroll migrate examples/ --backfill-batch-size 500 --backfill-batch-delay 100ms
```

These options help manage the performance impact of large backfill operations by processing data in smaller batches with optional delays between batches.

## Abort on multiple unapplied migrations

By default, `pgroll migrate` will apply all unapplied migrations. However, it may sometimes be desirable to only apply a single migration to ensure that an existing version schema is not removed by a sequence of migrations. In this case, running:

```
$ pgroll migrate examples/ --expect-one
```

will cause the command to fail if more than one unapplied migration is detected.

## A Column Filled for the Previous Version

An `add_column` with `up` installs a trigger that fills the new column for writes made through the previous version schema. Completing the migration removes the trigger. Without `--complete`, `pgroll migrate` completes every migration but the last as it goes, while applications on the previous version keep writing until `pgroll complete`.

So `pgroll migrate` refuses, before applying anything, a run in which such a migration is followed by others. Apply up to it, finish that deployment, then run again:

```
$ pgroll migrate examples/ --to 03_add_column
$ pgroll complete
$ pgroll migrate examples/
```

The refusal does not apply with `--complete`, with version schemas disabled, to a table created since the last `pgroll complete`, to an `up` that is the column's `default` as written or `COALESCE(<column>, <default>)`, or to a migration that also holds an operation that waits for `pgroll complete` (a column or table drop or rename, an `alter_column`): its trigger stays until then.

## An Open Train

`pgroll migrate` and `pgroll start` refuse to run when earlier migrations are applied but not contracted, one of them still has a trigger installed, nothing is in progress, and the latest migration's version schema exists. Applications running on that schema would be a third revision beside the previous deployment's and the new one's, and the triggers of the migrations still expanded can tell only two apart.

A bounded `pgroll revert --to` leaves this state. Run `pgroll complete` to contract the open migrations first, or `pgroll revert` to undo them.

`pgroll materialize` after an interrupted `pgroll migrate` leaves it too. When no application is pinned to the materialized schema, resume with:

```
$ pgroll migrate examples/ --leaf-unpinned
```

Neither command refuses with `--complete`, which pins nothing.

`pgroll materialize --migrations` refuses in the same state: the triggers would follow the schema it projects and rewrite what applications on the latest migration's schema write. Contract first, materialize without `--migrations`, or pass `--leaf-unpinned` when no application is pinned to that schema.

## Existing Database Schema

If you attempt to run `pgroll migrate` against a database that has existing tables but no migration history, the command will fail with an error message. In this case, you should first run `pgroll baseline` to establish a baseline migration that captures the current schema state before applying any new migrations.
